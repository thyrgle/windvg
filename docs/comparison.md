# wvg compared: TikZ, SVG, and the neighbors

wvg is a small declarative drawing language with a parametric model
(tracks, point algebra, generators) and a byte-exact multi-host
conformance discipline. This page records how it compares to the systems
people reach for instead — especially **TikZ/PGF**, the deepest 2-D
drawing language in wide use — what wvg is missing, where it wins, and
what it deliberately will not do. It is the source for the version
roadmap: **v6 = language power (constants + repeat), v7 = geometry
(arc-between + intersections)**.

## The one-paragraph version

wvg is not a TikZ replacement or an SVG replacement. It is a *data
format*: a drawing is a document, not a program. TikZ outclasses it in
raw expressive power — loops, macros, math, intersections, decorations,
plotting. wvg outclasses TikZ in universality (three independent
implementations agreeing byte-for-byte), in latency (live re-resolution
in milliseconds on a phone, versus a TeX toolchain compile), and in
safety (documents are serializable data with no evaluation surface).
Worked examples of the same drawings in all three languages — with
line-count and character-count comparisons ([`count.py`](../../comparison/count.py)
reproduces the tables) — live in
[`../../comparison/`](../../comparison/).
The roadmap exists to close the gaps that matter without giving up any
of those three properties.

## Dimension by dimension

| Dimension | TikZ / PGF | SVG | wvg |
| --- | --- | --- | --- |
| Nature | macro language on top of TeX (Turing-complete) | XML scene format with scripting hooks | declarative document, data only |
| Implementations | one (the TeX/pgf engine *is* the spec) | many renderers, behavioral differences | 3 hosts (Python, Rust, Kotlin) byte-exact on a golden corpus |
| Round-trip fidelity | no — output is PDF/SVG, source is lost | yes (it is a file format) | yes, exact — emitters reproduce the IR |
| Interactivity | batch: seconds per compile | live (browser) | live: sub-millisecond resolve, editor round-trips gestures ↔ source |
| Parametric geometry | calc library, string-macro substitutions | none | track protocol: anchors, between, polar, tangent offsets, generators — one uniform model |
| Repetition/abstraction | `\foreach`, macros, styles | `<use>`, CSS | defs/use (shapes), generators; repetition = v6 |
| Paint/effects | shadings, patterns, fadings, decorations | filters, masks, blends, dashes | flat + linear/radial gradients, markers; clip/patterns/dash = Tier B/C (see `format-review`) |
| Text | full TeX typesetting | rich but engine-dependent | v4 text (tier B): anchors + measured widths, sans only |
| Output targets | PDF (SVG via drivers, lossy) | itself | SVG, PNG, TinyVG (byte-exact), self |
| Safety | code execution (documents can do anything) | scripts, external refs | no evaluation surface; documents are inert data |

## Where wvg outshines TikZ

1. **Conformance discipline.** TikZ's spec *is* its implementation; output
   varies by engine version and driver. wvg has a written EBNF grammar, a
   versioned additive spec, and three independent implementations pinned
   to a byte-exact golden corpus (16 documents, checked in CI).
2. **Universality of the runtime.** The full resolver compiles to Rust and
   Kotlin and re-resolves a typical document in well under a millisecond —
   which is why an Android editor can round-trip gestures and source
   losslessly in real time. TikZ requires a TeX distribution; no live
   editor exists for it.
3. **The track protocol.** Every shape is a 1-D arc-length track, and one
   uniform model drives anchors (`@track pct`), generators
   (`along align=tangent`), stroke markers, and tangent offsets
   (§7.20). TikZ reaches the same results through separate packages
   (`calc`, `decorations.markings`, `pos=`) with unrelated syntaxes.
4. **Composable point algebra.** `between` extrapolates past its
   endpoints, `polar` nests with any point, `from` projects onto any
   track, `tangent` rides any track at any screen-space angle — all valid
   in any point slot, including inside `def`s. TikZ's coordinate
   calculations are macro-textual and context-sensitive.
5. **Documents are data.** No macro expansion, no evaluation, no
   injection surface; documents diff cleanly, serialize safely, and can
   be generated by other tools. TikZ documents are programs — that is
   their power and their liability.
6. **Grid guides.** Invisible, anchorable scaffolds that participate in
   the track protocol but never reach the output. TikZ's equivalent
   (helper coordinates or overlay nodes) leaks into the source semantics.
7. **Fidelity policy.** Every construct is explicitly Tier A (encodes to
   TinyVG), Tier B (wvg/SVG only, compile refuses by default), or
   Tier C (needs TinyVG changes). Users know exactly what survives where.
   TikZ gives you whatever the driver happens to produce.

## What wvg is missing vs TikZ — ranked, with the wvg answer

Each gap lists TikZ's offering, the design-compatible answer, and where
it lands on the roadmap. The ordering is by value multiplied by fit with
the language's philosophy.

### 1. Repetition with parameters — `\foreach` (v6)

TikZ's `\foreach \i in {1,...,12} { ... }` is the workhorse: one loop
draws twelve ticks *and their labels*, a family of parameterized cells, a
whole tree. wvg's generators (`along`, `polar`, `grid`) cover only
"motifs along tracks" — statement-level repetition does not exist.

The wvg answer is a **bounded `repeat`**: fixed count, an index exposed to
the body (substituted into numbers and point expressions), no recursion,
no arbitrary math, no early exit. It stays data — every expansion is
computable without an evaluator — while closing most of the practical
gap. Target: v6, together with constants (below).

### 2. Named constants — `\newcommand` / `let` (v6)

"Gear radius = 50" currently means editing every `50` in the document.
`defs/use` reuses *shapes*; scalars have no name. The wvg answer is
named constants usable anywhere a number or point is expected — no
arithmetic in v1 (constants are values, not expressions). This converts
documents from coordinate soups into parameterized drawings, and
multiplies the value of everything else (generators, defs, tangent
offsets). Target: v6, before or with `repeat`.

### 3. Curved connectors — `to[out=.., in=..]` (SHIPPED in v7)

Diagram work constantly needs "an arc from p to q, leaving at angle a,
arriving at angle b" (or bulging by X). wvg's path arcs are
ellipse-parameter instructions, so connectors require hand-computed
centers today. The answer is an `arc between p q` shape (or a
`connect` point/edge form) with in/out angles or a bulge parameter —
small grammar, large ergonomic win. Target: v7.

### 4. Path intersections — `intersects` library (SHIPPED in v7)

Given two named paths, TikZ computes their crossing points. This is
*natively* wvg: both operands are already tracks with flattened
geometry, so Shipped in v7 as the `intersects a b [k]` point form: 257-point track
chains through `point_at_distance`, the normative crossing formula,
k-th crossing in chain order. Bounded, deterministic, byte-exact across
hosts.

### 5. Clipping and masks — `\clip` (Tier B/C; format-review W6)

Bread-and-butter TikZ. Already on the roadmap: masks are Tier B (wvg/SVG
only), clip is Tier A-hard or Tier C because TinyVG 1.0 cannot express
it. Unchanged; see `format-review.md`.

### 6. Patterns and dashes — hatch fills, dashed strokes (Tier B; W4)

Hatching is the classic TikZ fill. Dashes and patterns are strokes/fills
TinyVG cannot encode — Tier B with the established fail-by-default
contract. Unchanged; see `format-review.md`.

### 7. Richer text — nodes with boxes, `fit`, rotation (Tier B, v-next)

TikZ nodes are typeset boxes: backgrounds, frames, rotation, and the
`fit` library (a node that bounds other nodes). wvg text (v4) has
anchors and measured widths but no rotation, no background box, no
multi-line, no fit. A background/frame variant and rotation are
straightforward Tier B extensions; `fit` is a point/shape computed from
other nodes' bounding boxes — genuinely useful and philosophically fine
(bounds are already tracked). Post-v7.

### 8. Plotting and data — `\draw plot` (deliberate exclusion)

TikZ plots coordinate lists and functions (with pgfplots, entire
charts). wvg will not absorb this: data-driven drawing is the job of a
*generator that emits wvg* — a script, notebook, or future companion
tool. The language stays closed-form; polygon/polyline already accept
any computed point list such a generator produces. Recorded here so the
exclusion is a decision, not drift.

## Deliberate exclusions (with rationale)

- **3-D and perspective** (`xyz` coordinates, 3-D plot): wvg is a 2-D
  format compiled to TinyVG; 3-D belongs to a projecting front-end.
- **Graph/tree auto-layout** (child syntax, layered/spring layouts):
  that is DOT/graphviz's territory; layout algorithms are a service, not
  a language feature. wvg consumes their output beautifully via grids
  and anchors.
- **Math typesetting**: a renderer concern; wvg text is honest about
  being plain strings.
- **A macro/programming layer**: the one exclusion that defines all the
  others. Power arrives as *more declarative constructs* (repeat,
  constants, intersects), never as an evaluator.

## Roadmap summary

| Version | Theme | Items |
| --- | --- | --- |
| v6 | language power | named constants, expressions, bounded `repeat` |
| v7 | geometry | `arc_between` connectors, `intersects` point form |
| v-next | rendering (Tier B) | clip/masks, patterns, dashes |
| v-next | text | rotation, background box, `fit` |
| — | excluded | plotting, 3-D, auto-layout, macros |

Version assignment is a commitment of intent, not a schedule: each
version ships through the usual pipeline — spec first, then the Python
oracle, then byte-exact Rust and Kotlin implementations with goldens.
